# Mindustry 微信小游戏重构方案

日期：2026-09-14；进度更新：2026-09-15。状态：架构基线，已有物流原型；实际交付与未验收项见 [03-开发进度](03-开发进度.md)。

本文以当前仓库 Mindustry（检查版本 `174f166e88`）为重写对象，采用 Cocos Creator，目标是轻量单人微信小游戏。配套执行安排见 [02-开发计划](02-开发计划.md)。

## 1. 目标与范围

保留「采集资源 → 铺设运输线 → 加工材料／供给弹药 → 建造防线 → 抵御波次」的核心体验，做成适合手机触屏的短关卡游戏。

用户已确定：采用 Cocos、发布微信小游戏、定位轻量、不需要多人联机、不需要地图编辑。以下关卡数量、内容规模、操作方式与性能指标是本方案的建议基线，可在原型阶段按试玩结果调整。

### 1.1 首版产品基线

| 项目 | 首版建议 |
| --- | --- |
| 模式 | 单人关卡，首次加载资源需要网络，资源就绪后战斗不依赖业务服务器 |
| 视角 | 横屏、2D 俯视、网格建造 |
| 时长 | 教学关约 5 分钟，普通关约 8～12 分钟 |
| 关卡 | 5 张人工配置地图，每关约 5～12 波；逐关解锁 |
| 地图 | 教学 48×48，普通 64×64；首版上限 96×96 格 |
| 内容 | 3 种资源、10 类建筑、3 类地面敌人 |
| 玩家身份 | 指挥视角直接建造；首版不实现可驾驶机甲、手动射击和友军单位指挥 |
| 成长 | 关卡解锁、通关记录；每局资源重新初始化 |
| 持久化 | 本地设置、进度和一个当前关卡续玩档 |
| 商业化 | 首版不接广告、付费、排行榜、分享奖励；后续独立评估 |

### 1.2 功能取舍

| 原版能力 | 决策 | 小游戏实现 |
| --- | --- | --- |
| 采矿、传送带、加工、弹药供给 | 保留核心 | 精选少量资源和配方，物流必须真实影响生产与防守 |
| 建造、旋转、拆除、生命值 | 保留并简化 | 即时建造，资源不足则拒绝；拆除按配置返还部分建材 |
| 炮塔、敌人、波次、核心存亡 | 保留 | 地面敌人和两类炮塔，固定波次表 |
| 战役、星球、区块远征、跨区物流 | 替换 | 线性关卡选择和本地解锁 |
| 电力、液体、复杂工厂链 | 首版排除 | 钻头与工厂直接工作，避免首局同时学习多套网络 |
| 单位制造、空军、海军、控制机甲 | 首版排除 | 敌人仅地面寻路，玩家专注布局 |
| 多人、房间、聊天、同步、服务器 | 明确排除 | 无网络对战及相应运行时模块 |
| 玩家地图编辑、导入导出、地图分享 | 明确排除 | 地图随版本提供；开发人员编辑 JSON 配置，不开发地图编辑器 |
| 蓝图、逻辑处理器、Mod、脚本扩展 | 首版排除 | 只加载受控配置，无玩家代码执行入口 |
| 原版存档与地图格式 | 不做运行时兼容 | 使用独立 JSON 数据格式，首版关卡重新制作 |

「不需要地图编辑」不影响游戏内建造：玩家仍可在允许区域放置建筑，但不能修改地形、矿点或敌人出生位置。

## 2. 现有工程与重写策略

当前工程为 Java 17 多模块 Gradle 项目，共享玩法位于 `core/src/mindustry/`，客户端入口分布在 `desktop/`、`android/`、`ios/`，另有 `server/`。`settings.gradle` 支持引用相邻 Arc 工程。它不适合通过增加一个微信入口直接完成迁移。

已检查的代表代码表明：`Conveyor.java` 同时引用 Arc 渲染、内容注册、建造和生成实体；`Logic.java` 涉及波次、事件与战役；`SaveIO.java` 使用 MSAV 文件头、压缩流和多版本读写。这些是玩法分析依据，不应成为新工程必须继承的依赖。

| 原路径（相对仓库） | 可参考内容 | 新模块与处理 |
| --- | --- | --- |
| `core/src/mindustry/core/World.java`、`world/` | 格子、地形、占用、建筑关系 | `domain/world`，重新设计紧凑网格 |
| `world/blocks/production/Drill.java` | 采矿条件与产量 | `domain/production`，只保留矿点判断与计时产出 |
| `world/blocks/distribution/Conveyor.java` | 方向、容量、堵塞 | `domain/transport`，固定容量和分阶段转移 |
| `world/blocks/production/GenericCrafter.java` | 输入、输出、加工进度 | 数据驱动配方与统一加工系统 |
| `world/blocks/defense/turrets/`、`entities/` | 弹药、射击、伤害 | `domain/combat`，精选机制重写 |
| `ai/Pathfinder.java`、`game/Waves.java` | 路径与刷怪组织 | `domain/pathfinding`、`domain/waves` |
| `content/` | 内容定义方法 | `content` 下独立定义，稳定字符串 ID |
| `input/MobileInput.java`、`ui/`、`graphics/` | 交互与视觉参考 | Cocos 输入、UI 和渲染重新实现 |
| `io/SaveIO.java`、`game/Saves.java` | 备份、版本化思路 | `application/save` + 平台存储适配 |
| `net/`、`editor/`、`mod/`、`logic/` | 本次不使用 | 不建立对应模块 |

上表简写的 `world/`、`ai/` 等均位于 `core/src/mindustry/` 下。

建议在本仓库新增独立 `cocos/` 工程，原 Java 工程用于玩法对照；Cocos 工程不加入 Gradle 构建。采用分阶段重写：先实现一个可完整胜负的关卡，再扩展内容。不要批量翻译全部 Java 类，也不引入 JVM／Arc／原生库兼容层。

原仓库 [LICENSE](../../LICENSE) 标示 GPL v3。复用代码与素材前建立来源、许可和署名清单；字体、音乐、图片逐项记录，不默认与根许可证相同。是否复用及其发行安排在开工阶段确认，未确认素材先使用占位资源。本方案不对具体发行方式作法律结论。

## 3. 目标架构

### 3.1 技术选择

以用户提供的 Creator 4.0 文档作为参考基线；M0 使用实际可安装且可构建微信小游戏的版本完成 iOS／Android 真机验证后，锁定具体补丁版本、微信开发者工具版本及调试基础库版本。文档地址不代表本机已经安装对应编辑器。

使用 TypeScript 和 Cocos 2D 能力。战斗逻辑采用普通 TypeScript 数据与系统，Cocos 组件负责画面、输入和声音。首版不使用通用物理引擎；网格寻路、范围查询与子弹碰撞自行实现。先使用简单数组／对象池，不建设通用 ECS 框架。

### 3.2 目录建议

以下为目标结构，已实现目录以 `cocos/` 和开发进度记录为准。

```text
cocos/
  assets/
    scenes/                 # Boot、Menu、Battle
    scripts/
      domain/               # world、build、transport、production、combat、waves
      application/          # GameSession、命令、加载编排、存档
      presentation/         # 地图、建筑、单位、特效、UI、输入
      platform/             # PlatformService、WeChatAdapter、PreviewAdapter
      content/              # 配置类型、解析和校验
    bundles/
      common/               # 共用图集与声音
      chapter01/            # 首版关卡及独有资源
    resources/              # 仅确需 resources 加载的少量启动资源
  tools/                    # 配置校验、资源清单、包体统计
  tests/                    # 纯逻辑测试与确定性场景
  settings/                 # 编辑器生成并纳入管理的项目设置
  package.json
  tsconfig.json
docs/cocos/
```

Bundle 边界需在编辑器中配置；创建同名目录本身不会完成分包。提交 `.meta` 与项目设置，排除 `library/`、`temp/`、构建产物和个人配置。

### 3.3 依赖与执行顺序

```text
触屏输入 / UI → GameSession 命令队列 → domain 状态与系统
                                         ↓
                               只读快照 / 变化事件 → Cocos 视图
GameSession → PlatformService → 微信适配 / 浏览器预览适配
```

- `domain` 不导入 `cc`、`wx`、DOM、文件系统或 UI。
- 唯一状态源为 `WorldState`；Cocos 节点的位置和动画不决定战斗结果。
- 固定逻辑步长建议 1/20 秒，显示目标 30／60 FPS，移动在显示层插值。
- 每步依次处理建造命令、采矿与加工、物流转移、刷怪与移动、射击与伤害、胜负判定；同一步产出可进入物流，刚收到的加工材料在下步使用。
- 使用累积时间推进，单帧最多补 4 步；持续超载时先减少特效和展示数量，并记录异常。切后台立即暂停，回前台清空时间积压，不补算离线战斗。
- 游戏随机数由独立种子驱动，便于问题复现；不为不存在的联机需求实现锁步协议。

## 4. 核心规则与数据

### 4.1 首版内容清单

| 分类 | 内容 | 约束 |
| --- | --- | --- |
| 资源 3 种 | 铜、煤、石墨 | 铜用于基本建设及普通炮塔弹药；煤加工为石墨；石墨用于重型炮塔建设及弹药 |
| 建筑 10 类 | 核心、钻头、传送带、路由器、交叉器、仓库、石墨工厂、普通炮塔、重型炮塔、墙 | 核心由地图预置；其余逐关开放；无电力和液体依赖 |
| 敌人 3 类 | 普通、快速、重甲 | 首版用速度、生命、攻击和伤害减免区分，避免多套行为树 |
| 地形 | 地面、不可通行岩石、矿点、出生区域 | 地形不能由玩家编辑 |

开始资源确保能搭起「钻头 → 传送带 → 核心」和第一座防御塔。建筑费用从核心库存扣除；仓库存货不自动计入核心。工厂与炮塔依赖实际输入，不从全局库存远程取料。

### 4.2 地图与建造

地图配置包含 `schemaVersion`、`mapId`、`revision`、尺寸、地形／矿点数组、预置建筑、出生点、波次、初始资源、可用建筑及胜利条件。静态地图与运行中状态分开保存。

网格用整数坐标和稳定实体 ID。地形、矿点与占用分层；多格建筑由锚点和足迹定义。建造先校验边界、占用、矿点、资源和出生区，再统一提交扣费与占格；失败不得部分扣费。首版批量铺带采用整条预览、整条校验、整条提交。

敌人以核心为目标，避开不可通行地形，允许攻击挡路建筑。移动采用共享到核心的距离场，建筑作为有限破坏代价，不允许堵路后敌人永久停住。地形固定时复用基础路径信息，建筑变化触发有预算的脏更新；运行时用短距离避让处理单位聚集。距离场尚未刷新时沿旧路径接近障碍并攻击，禁止每个敌人每帧完整寻路。

### 4.3 物流与生产

- 每段传送带具有方向、固定容量、物品槽位和运输进度；画面中物品按需展示。
- 运输分为「读取上一步状态、生成转移意图」和「统一提交」两阶段；同一物品每步最多跨一条连接，避免数组遍历顺序改变吞吐量。
- 下游满载则等待；路由器按轮询顺序分配合法出口；交叉器两条通道隔离；多个输入竞争同一剩余容量时按固定顺序并轮换优先级。
- 接收物品前检查类型与容量；工厂只接收配方材料，炮塔只接收对应弹药。UI 显示缺料、满仓、缺弹三类状态。
- 加工开始时扣输入，完成时放入输出缓存；输出满则保留完成状态，腾出空间后交付一次，避免丢料或重复产出。
- 拆除返还比例、运输速度、产量和伤害全部配置化。建议拆除返还 50% 建材，建筑内部存货销毁并给出提示；敌人摧毁不返还。

### 4.4 战斗与结算

炮塔定期查询附近敌人，命中由逻辑坐标计算；使用空间网格筛选，子弹用线段扫掠避免低逻辑帧率穿透。弹药、冷却、伤害结算与死亡事件只处理一次。

波次配置为敌人类型、数量、出生点及间隔；同时存活达到上限时延后出生，不丢弃波次数量。最终波全部生成且敌人清空、核心存活才胜利；核心生命归零即失败。进度写入使用关卡 ID 与完成标记，重复打开结算页不重复解锁或发放结果。

### 4.5 存档与生命周期

存档包含 `schemaVersion`、`contentVersion`、地图 ID／修订号、逻辑 tick、随机数状态、实体 ID 分配状态、核心库存、建筑生命／方向／缓存／加工进度、传送带槽位、敌人与子弹状态、波次游标与计时器。寻路缓存、Cocos 节点、粒子和 UI 不保存，恢复时重建。

单档建议不超过 1 MB，采用主档／备份档和递增序号、校验信息。写入新槽并校验成功后再切换有效记录，失败保留旧槽；这是应用层恢复协议，不假设平台支持跨键原子事务。读取时选取最新有效版本，坏档回退备份；不支持的新版本提示重新开始当前关，独立的已通关进度尽量保留。

建议每 15 秒、波次结束及主动退出时生成快照；切后台执行短小的最终保存，但不能依赖后台回调一定写完。前台恢复显示暂停面板，由玩家继续；不提供离线收益。清理微信数据或换设备可能失去本地进度，首版在设置页说明，不将本地存储包装成云存档。

## 5. 微信平台与资源方案

### 5.1 已核对的平台事实

按 [Cocos 微信小游戏发布文档](https://docs.cocos.com/creator/4.0/manual/zh/editor/publish/publish-wechatgame.html)，小游戏环境不等同浏览器，构建需要配置 AppID 和设备方向；默认输出位于 `build/wechatgame`（随构建任务名变化），含 `game.json`、`project.config.json`。文档列出的主包上限为 4 MB，且禁止远程下载脚本。实际提审以当时微信规则和工具校验为准。

资源组织参考 [Asset Bundle](https://docs.cocos.com/creator/4.0/manual/zh/asset/bundle.html) 和 [小游戏分包](https://docs.cocos.com/creator/4.0/manual/zh/editor/publish/subpackage.html)。Bundle 是资源组织单元，平台分包是交付方式，需实际构建检查二者映射及跨包依赖。

### 5.2 本项目的加载设计

主包只容纳必要代码、启动场景、加载 UI 和极少启动资源，建议预算 ≤3.5 MB，为构建差异留余量。M0 必须先验证裁剪后的引擎加业务代码能否满足预算，再决定代码分包方案。

首版优先使用随版本上传的小游戏分包承载关卡与通用素材，不默认增加 CDN。进入首关前下载必要包，完成后不依赖持续联网；首次加载或本地缓存被清理后仍需要重新下载。其他关卡按需加载，下载失败提供重试与返回菜单。

只有打包报告证明需要时再启用远程纯资源 Bundle；届时增加资源域名、HTTPS、版本目录、发布校验和回退流程，不下发远程业务脚本。避免主场景静态引用后续关卡资源导致被提前打入首包。

`PlatformService` 首版只封装存储、前后台、屏幕／安全区、音频状态和必要错误信息；业务不直接调用 `wx`。浏览器预览提供相同接口的本地实现。首版无需登录、云开发或游戏业务服务器。

资源采用按场景拆分的静态图集、精简字库和短音效；先使用普通 Sprite 与对象池，地图按块组织并剔除屏外显示。物品与特效显示数量设上限，逻辑数据不因显示剔除而消失。退出 Battle 时归还对象、注销监听、释放关卡独有资源，保留确实共用的资源。

### 5.3 触屏交互

默认浏览模式单指拖动地图，双指缩放；选中建筑后进入建造模式，单指预览／铺设、按钮确认，独立按钮旋转与取消，双指仍可移动视野。区分两种模式，避免拖图时误建造。传送带展示箭头、转弯和费用，拆除使用独立模式与预览。

HUD 展示核心血量、资源、下一波倒计时和暂停按钮；建筑详情显示输入输出与停工原因。适配横屏安全区及微信胶囊区域，操作按钮建议至少 44 个逻辑像素，具体换算按设计分辨率与真机触摸验证。

## 6. 性能预算与验证方法

以下都是项目验收目标，不是微信平台保证或已测结果。M0 选定并记录一台低端 Android、一台主流 Android、一台较旧且支持目标微信版本的 iPhone，以及一台主流 iPhone；后续同设备同场景比较。

| 指标 | 建议基线 | 验证方式 |
| --- | --- | --- |
| 主包 | ≤3.5 MB，且通过平台限额校验 | 正式构建报告与微信工具双重检查 |
| 首关首次所需下载 | 累计 ≤8 MB，含主包和依赖包 | 清缓存记录完整加载链路 |
| 首次进入可操作首关 | ≤8 秒 | 10 Mbps、100 ms RTT 测试网络，10 次冷启动看 P90 |
| 已缓存进入可操作首关 | ≤3 秒 | 重启进程，10 次看 P90 |
| 低端机性能 | 正常速度下 P95 帧耗时 ≤33.3 ms；逻辑步 P95 ≤10 ms | 最大规模场景运行 10 分钟，排除加载阶段 |
| 主流机性能 | 争取 P95 帧耗时 ≤16.7 ms | 同场景真机测量；不作为首版低端门槛 |
| 内存 | 峰值目标 ≤200 MB，10 次进出战斗后稳定占用增长 ≤10% | 记录工具口径、设备及资源释放后的稳定值 |
| 压力场景 | 96×96 格、600 建筑（含 400 段带）、120 敌人、240 逻辑子弹 | 固定种子场景，同时达到这些规模 |
| 绘制 | Draw Call 目标 ≤100，特效与物品视觉实例预算化 | 帧分析；超标先查材质、图集和层级 |
| 稳定性 | 连续 30 分钟不崩溃，20 次前后台切换可续玩 | iOS／Android 均执行 |

若未达标，按测量结果依次处理无效更新、对象分配、空间查询、地图绘制和资源释放；再减少粒子与物流视觉实例。必要时收缩地图及同屏敌人数量并同步关卡配置，不能通过漏算伤害、吞物品或跳过逻辑达标。自定义批量网格渲染只在普通方案确有瓶颈后引入。

## 7. 关键风险与决策

| 风险 | 处理方式 | 决策时点 |
| --- | --- | --- |
| 内容缩减后失去物流乐趣 | 首关必须存在供给不足导致停火、补线后恢复的可观察反馈 | M2 试玩 |
| Java 重写工作量膨胀 | 依据独立行为规格重写，不追求原版全部细节一致 | M0 冻结范围 |
| 引擎包体／真机不达标 | 第一周完成可运行构建与压力原型，先验证后扩内容 | M0 |
| 堵路、环形传送带等边界 | 固定规则、守恒测试、无路攻击策略 | M1～M2 |
| 资源授权状态不清 | 来源清单；未确认资源用占位或自行制作 | M0，发布前复核 |
| 中断造成档案损坏 | 多时点快照、主备恢复、版本化迁移 | M3 |
| 关卡制作和数值时间低估 | 固定 5 关和 10 类建筑，内容与引擎任务分开估算 | M2 后复估 |
| 平台账号／审核时间不可控 | 提前准备真实 AppID、测试权限、届时要求的发行材料 | M0 启动，M5 检查 |

首版成功标准：玩家能在微信真机完成从建造物流到守住最后一波的完整游戏，暂停退出后能够续玩，五关内容和性能达到约定门槛。后续若增加电力、更多关卡或激励广告，应单独评估内容、包体、存档与周期影响。
